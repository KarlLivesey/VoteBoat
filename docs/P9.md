## Other concrete cost candidates, not implemented

The native [barrier](../src/native/log_store.rs) synchronizes the WAL and then
publishes a manifest through file synchronization, rename and directory
synchronization. Mac paired records show unchanged physical call counts despite
Core415's instruction changes. A wider bounded ready quantum can amortize these
calls; a different publication representation could remove physical work, but
requires a complete recovery/format plan first. Recovery currently replays valid
complete frames beyond the old manifest boundary; that boundary also ensures
acknowledged prefix damage is not silently discarded. Session fencing, partial
tail handling, replacement selection and this damage detection remain required.

The [ready execution check](../src/runtime/clients/ready.rs) enumerates retained
pending commands separately for each candidate. [Counter admission](../src/application.rs)
rebuilds their unique-operation set each time, while BucketCounter clones and
replays pending application work. Source inspection therefore identifies repeated
work that grows with both ready width and pending count; it is not a measured CPU
fraction. A bounded application-owned batch admission context could build shared
state once, retaining per-original validation, receipt bounds, order and the
existing singleton fallback. Generic applications may depend on all predecessor
commands, so replacing these checks with operation lookup alone is insufficient.
Measure this on the actual application path; the minimal no-op framework does
not exercise the owning ClientRouter's application admission.

## Measurement boundaries

Framework overhead, volatile native-store CPU work and real quorum-durable
application results are different measurements. Do not label a simulated barrier
as device durability. Keep state/payload/retention equal across paired runs; count
useful operations separately from entries/proposals/transaction phases. Record
all refusals, conflicts, unknown outcomes and intended offering times.

Use existing diagnostics before adding instrumentation. Isolate compilation/tests
from timed trials, warm up separately, interleave baseline/candidate trials, and
include maintenance for sustainable acceptance. Initial short diagnostics locate
costs; they cannot establish long-run capacity or real-device power-loss behavior.

The historical250ms serial gate and shutdown timing remain recorded; neither is
the definition of lightning-fast transaction performance. Choose explicit real
application latency/headroom budgets against selected Linux/macOS deployments.
