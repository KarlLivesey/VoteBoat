## Minimum framework floor

Pinned OpenRaft reference: e88bb40707f2e511d8ecc44d31edcb1d814a11a8.
Its minimal benchmark has3 nodes, empty requests/responses, an in-memory BTree
log, a no-op application and function-call RPC. Published setup is MacM1-Max,
client runtime1 worker/server runtime16 workers,1024 warmup operations and a
default20 million operations rounded to complete equal client/batch workloads.
Each client waits for its write's applied result; batch4 consumes every result.
Rates count entries, not batch requests.

Re-run both pinned engines on matched hardware/configuration before asserting a
comparison win. A short synchronous/cooperative harness, different retained log,
or unsupported batch API is diagnostic only. Sum-of-many-groups throughput cannot
stand in for one group's result. Track p99, queue occupancy and errors as well as
throughput. The published curve is a floor, not a stretch target or achieved claim.

## Measurement boundaries

Framework overhead, volatile native-store CPU work and real quorum-durable
application results are different measurements. Do not label a simulated barrier
as device durability. Keep state/payload/retention equal across paired runs; count
useful operations separately from entries/proposals/transaction phases. Record
all refusals, conflicts, unknown outcomes and intended offering times.

Use existing diagnostics before adding instrumentation. Isolate compilation/tests
from timed trials, warm up separately, interleave baseline/candidate trials, and
include maintenance for sustainable acceptance. Initial short diagnostics locate
costs; they cannot establish long-run capacity or real-device power-loss behavior.

The historical250ms serial gate and shutdown timing remain recorded; neither is
the definition of lightning-fast transaction performance. Choose explicit real
application latency/headroom budgets against selected Linux/macOS deployments.
