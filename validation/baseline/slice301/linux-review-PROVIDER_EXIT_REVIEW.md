## Decision

No demonstrated production interface failure was found in the inspected promised replacement seams. The implementation has real public host injection, including an otherwise native assembly; this is not just an inventory of future APIs. One bounded reusable connector assertion gap is concrete and worth closing. Its absence is an evidence gap, not an absent product feature or a reason to implement external adapters. The already shared application, storage, scheduling, timer, admission, buffer, outbound and observer assertions should be counted before planning more conformance work.

The 108 inventory entries are not 108 independently replaceable providers. Chapter17 explicitly distinguishes fixed core invariants, replaceable mechanisms, and constrained policy/application inputs (`VoteBoat-Design-Pack/docs/17-native-first-composition.md:39–47`). Its catalogue names are design proposals (`:49–53`); related operations may share one provider, including the store's own durability tracking (`:80`). Request types, receipts, configuration commands, ownership/fencing helpers and lifecycle guards must not each acquire a fake interchangeable adapter. `NamespaceOwner` is intentionally sealed around the existing owner guards (`src/namespace_creation/application/owner.rs:16–42`); its underlying application and partition providers remain public. This preserves the stated fixed activation/fencing invariants rather than violating the host-interface promise.

The applicable gate is actual public injection, real native contract use, declared retained ownership/sharing, failed-construction cleanup, and the selected providers' meaningful operation/refusal histories. See `VoteBoat-Design-Pack/specs/component-contracts.md`, especially “Contract sheet,” “Required construction and lifecycle tests” and “Evidence boundary,” and chapter17 `:159–169`. A partial metadata review does not certify a backend, but neither does “partial” mean a product capability is missing. Arbitrary capacity extremes, future external formats, new adapter combinations, performance measurement and full P7 fault scope remain separate claims.

## Public assembly and replacement path

`src/runtime/node.rs:28–94` publicly exposes `NodeLocalParts<S,T,E,A,W,O,H>` and `NodeParts<...,C,F>`. Scheduler, timer, entropy, application, persistence worker, outbound queue, snapshot worker, connector and transport factory are generic parameters. `Node::from_parts` (`:220`) validates before service and returns the original selected parts on rejection (`:269–294`). Peer session and endpoint types come from `PeerConnector`, and `PeerTransportFactory<C::Session>` builds the selected transport. `ReplicaParts` permits the same borrowed components under the non-owning driver; it is not a second infrastructure owner.

`src/native/node.rs:29–64` binds those contracts to `FairScheduler`, `DeadlineQueue`, `JitterEntropy`, `NativeLogWorker<NativeLogStore<FileLogIo>>`, `NativeOutbound`, `NativeSnapshotWorker<NativeSnapshotStore<FileSnapshotIo>>`, selected connector and wire transport. This convenient alias fixes native defaults; replacing lower components uses public generic Node/worker/transport construction, not modifying the alias or patching Raft. `NativeLogWorker<L: LogStore>` and `NativeSnapshotWorker<S: SnapshotRetention>` use the same domain storage contracts as host stores. Alternative log engines replace `L`; they do not implement the native WAL's file layout or pass data through two WALs.

Host implementations in integration tests are downstream local types importing `voteboat`'s public API. `tests/support/node.rs:35–66` constructs a fully host-selected Node. `tests/worker.rs:694` runs host persistence providers through a real cluster history; the native variant uses the same generic cluster history. `tests/transport.rs:1355` puts a host outbound queue and fixture codec into the native driver. `tests/provider_conformance/snapshot_worker_native.rs:55` puts host snapshot stores under the real native worker. The latter two are particularly direct examples of changing a provider inside otherwise supplied infrastructure.

## One finite reusable assertion gap

`PeerConnector` promises accepted tickets retain ownership until exactly one terminal receipt and close drains/cancels accepted attempts without stopping a shared host reactor (`src/connect.rs`, trait at146 and preceding contract). The downstream runner `downstream_connector_uses_public_tickets_and_local_secure_session_type` (`tests/connect.rs:177–234`) exercises cancel while accepted but invokes `close` only after its request has already completed. The native scope/budget/time test (`:526–600`) is separate. Thus no single common assertion sequence currently demonstrates host/native **close with accepted work**, **post-close original-request refusal**, and **invalid budget/backward-time refusal preserving pending ticket, usage and deadline**. Production native paths have direct coverage; this is a bounded reuse/evidence gap, not an observed failing behavior.

Recommended smallest complete deliverable: one generic connector contract runner using an accepted non-completing `Accept` attempt, supplied ticket/request constructors and an adapter for bounded terminal polling. Run on the local HostConnector and TCP native connector; optionally selected QUIC connector if its existing fixture can be reused without new infrastructure. Checks: (1) zero completion budget releases neither ticket nor credit; (2) wrong ticket cancel leaves exact pending attempt unchanged; (3) oversized budget/backward time refuses and preserves usage/deadline; (4) close keeps accepted credit and does not immediately report drained; (5) new submission returns the exact owned request with Closed; (6) exactly original ticket yields terminal Cancelled, repeated poll stays empty and final usage/drain is empty; (7) another existing shared logical resource remains usable. Do not require one exact native protocol-close packet schedule or forge successful authentication in this cancellation-only runner. A deficient checker mutant which reports drained/releases credit on close would make its intended assertion sensitivity explicit, but is not a new provider feature.

There is **no second demonstrated production blocker** in this audit. Do not add broad workers, observers, scope or platform adapter projects solely because metadata does not list them. Their selected assertions above can be recorded as reviewed evidence without claiming exhaustive conformance. Remaining implementation work should follow a failing concrete assertion or a specifically advertised missing combination.

Record selected coverage and the connector result, then qualify the chosen native/host feature profiles on Linux/macOS through the parent's checks. No test in this read-only audit was executed. No claim covers Turso/RocksDB/Tokio or another future adapter; those must satisfy the real contracts and re-run selected histories before support is claimed (chapter17:163–165). No arbitrary live backend pointer swap, broad heterogeneous backend migration, exhaustive fault cross-product, allocation/throughput guarantee, security follow-up, Windows or P8 is added to feature exit. The provider audit itself is complete once its finite selected evidence is recorded and the one chosen connector gap is either checked or explicitly retained; “every future provider might fail” is not a perpetual baseline prerequisite.
