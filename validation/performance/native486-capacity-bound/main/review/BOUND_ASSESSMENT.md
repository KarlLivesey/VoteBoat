# Read-only Counter cardinality fastpath review

The proposal is sound for the current Counter and its public ProposalAdmission contract. This is a mathematical/source review, not executed conformance or performance evidence. Source reviewed after exact480 restoration: src/application.rs::Counter::validate_proposal; OperationId is the fixed built-in identity type, Counter dedup has no interior mutation under this immutable borrow.

Let R = max_operations - dedup.len(), with 0 <= R <= 1,000,000. For a raw pending sequence P of length n, the old algorithm builds D = distinct(P) minus committed dedup IDs. Its result for a syntactically valid candidate c is Ok(receipt_size) exactly when |D union ({c} minus committed IDs)| <= R. Hence if n < R, this cardinality is at most n+1 <= R: returning the same receipt size needs no membership lookup, sorting, hashing or tree. Pending payload bytes remain intentionally ignored by this seam; syntax of the candidate remains the first check.

For n >= R, buffer exactly the first R raw IDs, then replay those IDs followed by the untouched remaining iterator through the original exact algorithm. No original pending overflow can occur before observing R+1 items, because at most one novel distinct ID enters the set per item. Consequently buffering the first R cannot advance past an original early overflow. On fallback, identical IDs are checked in identical order; candidate membership and capacity happen only after pending ends. R=0 should enter the old fallback directly.

No size_hint may justify the fastpath or allocation. Preserve the original next() trace: malformed candidate polls neither next nor size_hint; n<R consumes through the first None and stops even for a non-fused iterator; n>=R buffers R Some values, then the fallback polls the remainder only as demanded by the old capacity logic. Use a direct bounded next/push loop rather than collect(), count(), nth(), or iterator-size-hint preallocation. These methods can invoke host-overridden methods or allocate from hints that the old for loop never uses. Iterator panics unwind local owned IDs without application mutation or retained cache. The observable success/error, receipt bound, pending polling/early stop, and application state are unchanged; allocation strategy and out-of-memory behavior are inherently changed, so do not promise identical allocator failure behavior.

Memory must be described precisely: Vec::new() avoids an R-sized allocation for empty/small pending when R is one million. Logical length <= R does not imply Vec capacity <= R: geometric growth can reserve above R. Either explicitly bound requested growth (falling back before a growth would exceed the chosen budget is also semantically valid), or disclose a conservative capacity bound. No cross-call cache, public API change, provider opt-in, new ownership generation, data format or persistent state is necessary. Fallback temporarily retains both the raw IDs and the old tree, so measure this near-capacity cost; do not advertise reduced memory everywhere.

## Acceptance controls before timing

- Keep a test-local copy of the old validator as a genuinely independent reference. Exhaustively compare small capacities, committed subsets, pending lengths below/at/above R, repeated committed/novel IDs, candidate duplicate/conflict IDs, and malformed candidate lengths. Compare receipt size, exact error variant, unchanged checkpoint/application state, and iterator next count.
- Explicit boundaries: R=0 with empty/committed/novel pending and candidate IDs; n=R-1, n=R, n=R+1; n<R with malformed pending payloads (still ignored); invalid candidate must not touch a pending iterator whose next and size_hint panic.
- Enforce no hint dependence with lying and panicking size_hint implementations. Non-fused [Some, None, Some] must stop at the same first None as the old loop. A sentinel/panic after the first capacity-overflow item must never be polled. Test a panic before the buffer boundary, caught by caller, leaving application checkpoint unchanged.
- Fallback must not exempt a committed candidate from an overflowing pending prefix. Duplicate-heavy prefixes crossing R must still reach later novel overflow at the same item as the old validator. Verify exact preserved retries and original outcomes after actual application/recovery using existing unaffected controls.
- Run affected application and client/provider configurations sequentially, strict formatting/Clippy and enabled hook. Existing480 ready-admission oracle continues comparing the optional ready context to the now-faster exact singleton validator.
- Retain all finite paired loaded/singleton/moderate/skew TCP/QUIC outcomes, CPU/RSS scope, refusals and group tails on both hosts. Current482 Linux whole-launch profile's ~57% Counter validation motivates this stage but neither proves a gain nor predicts tail causality. No measured result exists for this proposal yet.
