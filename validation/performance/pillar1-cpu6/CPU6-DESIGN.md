# CPU6: prepared entry batches with singleton and wide specializations

23 October 2026. Design-only handoff. Parent owns integration and any implementation release.

## One recommendation

Recommend one bounded **prepared-entry-batch representation**: carry a lone entry inline through proposal/pending/message ownership, and consume a wide command builder by assigning its receiving-core index/term and constructing its existing immutable backing facts in one traversal. Keep the canonical log's small owned pieces and wide shared pieces. This changes the construction and transfer of `EntryBatch`, rather than adding another completion owner.

These are two size specializations of the same owned batch lifecycle. They do not remove the same instruction. That is explicitly permitted by the CPU6 brief; CPU3/CPU5's historical common-instruction selection rule is not a current contract. The boundary is concrete: commands become an immutable, independently ownable suffix, then the same batch flows through the existing checked plan, fan-out and canonical installation. No request-port, receipt-buffer, commit-notice, volatile-turn or borrowed-summary change is included.

**Gain UNKNOWN.** Source supports the removals below, and existing profiles locate wide assembly/freezing and real singleton/core work. They do not establish singleton allocation self-time, exclusive freeze CPU, dynamic counts, dominance, or a likely acceptance result. This is a candidate worth implementing and falsifying, not a speedup or qualification claim. The larger scope targets transient entry-container lifetime and a per-original traversal, rather than another fixed scalar metadata copy. No experiment is requested as a prerequisite by this recommendation.

## Current contracts and the bounded schema

Current `EntryBatch` is a Vec-sized `Spans::{Empty,One(Span),Many(Box<[Span]>)}`; `Span` is an owned Vec or an Arc-backed immutable range. Batches below16 stay owned; wide backings seal facts once. `EntryRange` already borrows slices, so retaining real LogEntry storage avoids an application/API migration.

Proposed shape, descriptive only (no code was implemented):

```text
EntryBatch / batch-only representation:
    Empty
    Inline(LogEntry)
    OnePiece(Span)
    Pieces(Box<[Span]>)

canonical Span remains:
    Owned(Vec<LogEntry>)
    Shared { Arc<BatchData>, start, end }

private unbound command storage:
    one existing Vec<LogEntry>, constructible only as Command entries
    no borrowed receiving-core authority and no caller-supplied facts

bind_commands(storage, checked_first, current_term):
    length 1: move its sole LogEntry into Inline, release prior Vec if present
    length 2..15: assign checked index/term, retain ordinary Owned piece
    length >=16: assign index/term and fold intrinsic facts in ONE pass,
                 consume same Vec into the existing immutable BatchData
```

The single public addition can be `From<LogEntry> for EntryBatch` (or an equally explicit `from_entry` constructor). Existing logical iteration, indexing, equality, slices, edit and conversions remain usable for hosts. Representation-size/API compatibility is not a gate, but behavior and actual resource bounds are. The batch is no longer advertised as Vec-sized. Exact compiled sizes are unknown until implementation.

A private command-only storage wrapper is justified only to make the fused constructor's invariant unforgeable: ProposalBatch already owns private LogEntries created solely by `push`. Move that SAME allocation into an opaque internal wrapper in the log entry module, with capacity/reserve/push/read/consume operations needed by ProposalBatch. No second staging buffer, new owner, provider, crate or runtime. Its only push constructs a Command from full OperationId and owned CommandBytes; it exposes no mutable entries or index/term authority. If a safe minimal typed boundary cannot preserve allocation ownership, stop and return the concrete issue; do not copy the builder into a second representation or add unsafe layout conversion.

The receiving Raft still checks role/voter/transfer/fence/busy, current limits/count/capacity/largest/peak, retained-entry limit and last+count overflow BEFORE binding. Old/foreign builders take the receiving core's current first index and term. A builder never attests predecessor, membership, configuration, durability or permission to commit. Direct Event::Propose constructs the actual indexed entry directly into Inline; it does not allocate a Vec to call the new constructor.

For a wide command builder, refactor fact construction so assignment and the existing metrics/retained-payload/maxima fold share one mutable traversal. Sequence positivity/continuity/constant term follow the checked receiving-core range plus the actual assigned fields; no later comparison against just-written neighboring fields is needed. Preserve the existing fact semantics, overflow/unavailable behavior and shared range queries. Keep `SPARE_MAX`, the one actual spare-capacity release, immutable Arc ownership and mixed prefix-index construction/admission; arbitrary mixed command sizes can still require their real second index pass. This is construction fusion, not a claim that facts or scalars were missing. Generic raw/decoded/edited/recovered/configuration batches continue through actual inspection; they cannot call the trusted command-origin constructor.

## End-to-end ownership and work at each width

**Singleton:** Event owns its input; after ordinary admission an Inline batch owns the LogEntry/payload. Pending owns that batch through the existing append plan. Checked install moves the entry into the last canonical Owned Vec when one exists; otherwise it creates the first canonical owned piece, exactly the real long-lived storage required. Do not retain one inline canonical span per write or accumulate an ever-growing descriptor history. Narrow outbound selection that selects exactly one entry clones it into Inline directly, with owned payload semantics, instead of `to_vec`; `for_message` keeps this independently owned singleton with no hidden backing. Followers move that ownership through the same plan/install. Current canonical growth, occasional first-piece allocation, payload Arc clones, entry checks, all3 applications, receipt Vecs and replies remain. No universal per-round allocation count is inferred; the source removal is the transient singleton entry-vector creation/clone/drop sites when these actual arms run.

**Width231:** builder pushes/growth/copy/peak checks stay real. Binding assigns231 entries and folds the immutable facts in that traversal, replacing the separate full fact-inspection traversal after assignment. The same entry Vec becomes the shared backing; original fan-out already shares it. Canonical append, slicing, command content, mixed-index fallback and application3×231 stay real. Introduced work includes the new batch variant branches, potentially larger surrounding values and fused-loop register pressure. No builder-growth elimination, follower-copy multiplication, mixed-index removal or exact savings is claimed.

**Width515:** the same lifecycle binds515 entries, removing the corresponding separate inspection traversal without converting to a second command array. Existing spare-capacity shrink/realloc and retention charges remain; the observed freeze realloc is NOT credited as removed. Actual replication piece boundaries/byte headroom may differ from231 and must be observed. Introduced fixed-size effects/plans and compiler behavior are independently assessed at this width. Passing231 cannot qualify515, or vice versa.

Ordinary canonical singleton ranges and wide shared pieces remain backed by actual `LogEntry` slices. `EntryBatch::slices/iter/contiguous/get/first/last` borrow Inline with `slice::from_ref`, and preserve order/exact-size/double-ended iteration. Do not implement them by a hidden temporary Vec or a temporary LogEntry reference. Explicit `to_vec`/`edit`, multi-piece contiguous fallback and existing FIFO `Effect::Committed(Vec<LogEntry>)` materialization remain honest owned operations. An Inline slice0..1 clones into Inline; an empty range retains no payload. Existing multi-piece composition can use ordinary spans; single-result slicing/selection must intercept before a Span helper forces a Vec. Canonical EntryRange/StateMachine need no new synthetic entry-view API.

## State, lifetime, failure, cleanup and restart

State path: bounded command admission → current-core binding/finalization → immutable EntryBatch → checked plan owned by sole Pending → exact volatile token or actual durable admission/barrier → checked install → contiguous committed canonical borrow/owned FIFO position → actual application → exact original outcomes. Representation construction produces no externally escapable effect or new evidence token. Existing tokens/stamps/tickets alone authorize their existing stages.

Before admission/binding, refusal drops only the incoming original/batch; a failed push preserves prior accepted builder contents and all checked conversion-peak behavior. Consuming bind may modify its exclusively owned unbound storage because no application/persistent state has changed. Overflow or any construction/admission error drops that ownership and leaves no new pending state/output. No partially initialized public batch escapes.

Inline clones own their full payload lifetime; a borrowed slice cannot outlive the batch. Shared ranges retain their original Arc and hidden-byte charge. Canonical mutation cannot invalidate independently held messages. Pending retains a complete plan until the same checks permit mutation; failed predecessor/stamp/completion leaves it uninstalled before the existing fence/drop behavior. Successful install followed by a following-effect or reply failure is accepted progress, not rollback. No retry replays an applied interval to reconstruct lost outputs. Prior queued effects keep their original FIFO position; no new application callback or early reply is introduced.

Cancel/drop releases only the owner's Inline payload/Vec/Arc or message reservation when its actual terminal owner releases it. Drop one group without invalidating another's shared host resources. No pool, generation counter, root lock, detached job or retained receipt cache is introduced. Normal shutdown still drains/reports unresolved accepted work under the same public contracts.

No new persistent representation or protocol version is required: log/wire codecs serialize the same logical entries/fields. Decode/recovery still verifies actual bytes and constructs independently validated entries; no serialized `sealed` bit or restored pointer proof. A restarted core obtains its actual fresh incarnation and reconstructs canonical log, membership, snapshots, dedup/outbox/lineage normally. Old completions remain invalid. Default maintenance/compaction moves/slices the actual canonical storage; no retain-all mode, fresh-core replacement or deferred cleanup is allowed.
