2. **P2 — Complete the peers actually visited by flush.** `src/runtime/peers.rs:945–960`. The write loop skips idle peers and counts actual transport visits, but its final completion pass checks only the first `peer_visits` roster positions. With cursor at peer 2, peer 2 idle, peer 3 sending, and `peer_visits=1`, peer 3 writes its complete frame but returns no completion; its queue credit and accepted send slot remain held. The node consequently continues advertising write interest because its outbound queue is nonempty. This defeats the same-poll completion/wakeup objective for a supported budget (and larger sparse rosters). A temporary deterministic test in `tests/support/peer_driver_flush.rs` failed on the PR:

   ```rust
   let mut f = Fixture::new();
   f.attach();
   let ticket = f.enqueue(3);
   let p = f.flush_with(PeerDriverBudget {
       peer_visits: 1,
       ..Default::default()
   }).unwrap();
   assert_eq!(f.sent(3), 1); // passes: all bytes written
   assert_eq!(done(&p), [(ticket, LocalSendResult::Sent)]); // fails: []
   assert!(f.outbound.is_drained());
   ```

   Complete the actual visited peer IDs without moving the fair cursor or expanding the transport-visit bound. A temporary check calling `complete_send(outbound, peer, out)` for each successfully visited peer made this test and all seven existing flush tests pass. That experimental change was reverted.

3. **P2 — The claimed FIFO guarantee has an inherited small-send-budget hole.** `src/runtime/peers.rs:1327–1328`. This is **pre-existing, not attributed to N1**: `submit_sends` is byte-identical to main, and I reproduced the same failure using only its ordinary poll path. Nevertheless, it prevents certifying the requested FIFO guarantee on the newly reused path. Queue tickets 1, 2, 3 for the same peer/class, block that peer, and make three calls with `sends=1`. Ticket 1 is accepted; ticket 2 is staged/refused; the next bounded scan rotates ticket 2 behind ticket 3. Unblock, then poll with `sends=1`: completion/send order is **1, 3, 2**. Temporary deterministic tests reproduced this both after three flush calls and after three poll-only calls. Keep older refused work ahead of later same-peer/class work while permitting other peers to progress; add the budget-boundary regression test. This is distinct from the one-accepted-slot rule, which remains enforced.

The owner should preserve original order for every *in-place expansion*. That does not justify pushing every generic callback's new effects to the front: other snapshot callbacks perform new core transitions; their current internal producers have singleton output rather than this sibling Persist tail. **Batching recommendation.** The explanation is credible: shorter feedback cycles reduce entries per immutable Append, increasing frames and follower persist/barrier work; the supplied counters support it. It is attribution evidence, not proof that a proposed follow-up restores the loss. Keep the existing single flush **after the entire replica poll**—it is already outside the group-processing loop. Establish a bounded batching decision **before Append effects are created**, with immediate control/idle traffic and a bounded backlog batch/deadline policy for sustained writes; keep the final write-only flush for every effect that is emitted. Preserve the existing WAL-worker grouping as part of that design. Recheck durable-save CPU and networked latency/rate at equal cores.

The listed alternatives are not interchangeable fixes:

- Flushing once after all groups is already the call-site shape, and cannot fix a G=1 regression by itself.
- Deferring a peer merely because it has an Append "in flight" can defer the very unsent request whose creation installed that flag. It needs explicit states and a bounded deadline; delaying already immutable messages alone cannot merge their entry ranges. Put any batching delay before emission, and keep urgent control traffic immediate.
- Multiple outstanding Appends may improve utilization, but `Raft::requests` currently stores one exact range/context per follower. The transport/QUIC send window is not multi-request Raft correlation. Pipelining needs a bounded range/context window, correct ACK/retry/failure handling, and batching policy; it does not inherently produce larger Appends. Treat it as a separate Raft slice, not a small N1 repair.
- N2 can reduce framing/TLS costs across queued messages/groups. It does not restore entries per Append and is not sufficient evidence that the follower WAL-barrier regression is fixed.
